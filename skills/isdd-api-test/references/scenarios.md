# 常见 Java 接口场景

同一条取消订单用例可以混用两种做法。POST 后用 GET 验证保存结果时，让测试类内的 OrderStore 依订单号保存业务实际传入的值（可变实体要隔离副本）。验证重复请求时，让已有幂等端口依实际 key 占用。对 MQ 仅需检查事件内容和次数时，用 Mockito 捕获和校验发送参数即可。业务规则保留在真实 Service 中。共享 Spring 测试上下文时隔离各用例的状态。

| 场景 | 测试准备 | 接口验收重点 |
|---|---|---|
| 查询、分页、归属 | 在 Repository 或 MyBatis Mapper 边界提供多条混合数据；业务层负责的过滤保留真实 | ID、返回字段、顺序和可见范围。若过滤本身在 SQL 实现，标明 SQL 另验 |
| 写入后读取 | 使用一个保存实际入参并返回副本的小型内存 Repository；每条用例清理 | POST 得到的 ID 经过 GET 能读到正确状态；遗漏 save 应导致失败 |
| Redis 缓存或幂等 | 缓存抽象使用内存实现；幂等键保留首次和重复请求的状态 | 命中/未命中、同键重复请求只写一次；TTL、Lua 与分布式锁真实语义另验 |
| MQ 发布 | 捕获项目已有 Publisher 的事件；使用 Spring Cloud Stream 时可复用 Test Binder | 事件号、归属、载荷和次数；拒绝请求后没有误发。异步测试用有界等待 |
| 第三方失败 | 在已有远程客户端注入超时或拒绝 | 错误映射、补偿状态及是否重试，验证有业务意义的副作用 |
| 鉴权、校验与业务拒绝 | 使用约定的身份、真实安全规则、Advice 和 Validator | 分开断言 401/403/字段错误与已进入业务的拒绝；纯拒绝边界用例不能替代代表性业务场景 |
| 规则组合 | 在 UT 细分状态、金额和边界组合；用一条 HTTP 场景证实规则接入 | 原有单测和场景使用独立算出的预期；验证 response 和副作用，不复制生产算法 |
| 仅 Controller 有业务逻辑 | 真实 Controller 和领域对象，替换其 Repository 等出站依赖 | 在 scenario 声明真实 Controller；如有独立 Service 必须声明该 Service，不能用 Controller 绕开检查 |
| 无返回体或删除 | 验证约定状态及被删除条目的外部可观察效果 | 如 204 加上已删除、消息或后续读取结果；成功断言之后再关联目标请求 |

接口计数按 suite（模块/发布配置）、HTTP 方法、模板及参与分派的条件。每个新行为使用稳定场景 ID；同一路由可有多条。需要验证请求和消息序列时，把准备请求与被验收的操作区分开。对支付、数据迁移等风险沿用项目自身的审批深度。
