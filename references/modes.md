# 工作流模式

## 选择规则

默认使用 `standard`。只有全部 lite 条件都满足时才能选择 `lite`。出现任一 strict 触发条件时必须选择 `strict`。用户可以随时升级模式；降低建议模式前必须获得明确确认。

## 轻量模式（lite）

必须同时满足以下条件：

- 变更局部且容易回滚。
- 不修改数据库 schema、持久化数据、公共 API、事件契约或文件格式。
- 不影响认证、授权、支付、个人数据、密钥或安全边界。
- 不增加运行时依赖，不改变基础设施或部署行为。
- CodeGraph 显示影响范围小且已经理解。
- 存在已有的自动化或确定性验证路径。

归档保持精简，但不得删除要求章节。除非存在会改变范围或风险的不确定性，define 到 plan、plan 到 build 之间无需暂停确认。

## 标准模式（standard）

用于普通功能、缺陷、重构、内部 API 和跨文件变更。进入规划前需要确认需求，进入实现前需要确认计划。运行受影响区域要求的仓库检查。需求符合度和工程质量分开审查；平台支持时使用新鲜的只读审查 Agent。

## 严格模式（strict）

出现以下任一情况时使用：

- 认证、授权、支付、密码学、密钥或个人数据。
- 数据库或持久化数据迁移。
- 公共 API、协议、事件或兼容契约。
- 基础设施、部署、并发、分布式系统或不可逆操作。
- CodeGraph 显示高影响范围、核心架构边界或业务关键流程。

必须明确确认需求和计划，记录回滚或迁移细节，执行安全与兼容检查，并安排两个上下文隔离的只读审查智能体分别验证需求符合度和工程质量。

## 自动执行边界

只有 lite 分类完成后才能使用 `--auto`。它可以继续执行 plan、build 和 verify，但必须在外部发布、push、创建 PR、merge、deploy 或其他外部可见动作前停止。
